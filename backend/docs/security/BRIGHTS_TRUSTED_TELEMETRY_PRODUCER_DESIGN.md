# Brights Security Shield: Trusted Telemetry Producer Design

## 1. Status and purpose

This document specifies a proposed server-side event-production
boundary for Brights Security Shield.

It is a design contract, not an active collector, middleware,
authentication hook, storage system, or enforcement mechanism.

No runtime integration is authorized by this document.

## 2. Relationship to existing components

The existing pipeline consists of:

1. SecurityRequestEvent records.
2. aggregate_request_events for bounded, scoped event aggregation.
3. convert_aggregation_to_observation for independent validation
   and preservation of identity and UTC window context.
4. evaluate_abuse_observation for non-enforcing classification.

A future producer may supply evidence to this pipeline only
after the producer's trust and completeness requirements are met.

## 3. Producer trust boundary

The producer must distinguish application-controlled facts from
untrusted client input.

Client headers, URL parameters, user-agent values, arbitrary
request bodies, and unauthenticated claims are not authoritative
sources for event identity or authentication outcomes.

A server-side value is not automatically trustworthy merely
because a middleware layer can read it. Its provenance matters.

## 4. Canonical request identifiers

A canonical request ID must be generated by trusted server-side
code or supplied by a separately verified trusted internal system.

The producer must not adopt arbitrary X-Request-ID, traceparent,
or similar client-controlled headers as canonical request identity.

The same canonical request ID must be stable across verified
security outcomes belonging to one request.

Distinct requests, including actual retries, must receive
distinct canonical request identities.

Request ID format must conform to the existing bounded
SecurityRequestEvent identifier contract.

## 5. Timestamp authority

A trusted server-side clock must supply integer Unix seconds.

The producer must not use client-provided timestamps as authoritative
event times.

Existing fixed_utc_window rules determine half-open window
boundaries; the producer must not silently redefine alignment.

Clock skew, clock discontinuity, or unverified timestamps require
an explicit failure or unknown-data policy.

## 6. Identity scope provenance

ACCOUNT, ORGANIZATION, and API_CREDENTIAL identities must derive
from verified application-side authentication and authorization
context appropriate to the operation.

A user-controlled account or organization selector does not alone
prove an authorized identity scope.

The scope and identifier used by an event must describe the
specific verified subject being observed, without mixing subjects.

Scope identifiers must meet the existing nonempty, bounded,
whitespace-free identifier requirements.

## 7. Anonymous and network-peer scope

NETWORK_PEER is not interchangeable with a verified account
or authenticated identity.

Any network-peer identity must derive from the existing trusted
peer-address policy, not unverified forwarding headers.

A future design must explicitly specify normalization, privacy
handling, and identifier derivation before emitting NETWORK_PEER
events.

Unknown identities must not be silently assigned to a trusted
ACCOUNT, ORGANIZATION, or API_CREDENTIAL scope.

## 8. Endpoint classification

A producer must use the committed endpoint-risk classification
policy and its explicitly approved endpoint mappings.

UNCLASSIFIED or unknown endpoints must not be silently reclassified
as approved categories A, B, C, D, or E.

Where classification is unavailable, the event must be withheld
from category-specific aggregation and the coverage limitation
reported through the completeness policy.

## 9. Authentication failure provenance

authentication_failed=True must represent a verified outcome
from an authorized authentication-result producer.

An HTTP response status alone is insufficient evidence of a
specific authentication failure.

Authentication checks that are never instrumented must not be
represented as successfully observed failures or successes.

## 10. Authorization denial provenance

authorization_denied=True must represent a verified authorization
decision from the responsible server-side authorization layer.

An HTTP 403 response alone is not conclusive proof that such
a decision was captured.

Authorization failures and authentication failures may legitimately
co-occur on the same canonical request.

Neither counter is subtracted from the other.

## 11. Unknown and unavailable outcomes

Unknown is distinct from False.

A False event signal may be used only when the producer's
signal contract actually supports that assertion.

If the application cannot establish whether a relevant outcome
occurred, the producer must not invent a negative outcome.

Missing evidence must be represented through an explicit
incomplete or unavailable path rather than being mistaken
for normal activity.

## 12. Event ownership and scope isolation

Each SecurityRequestEvent must belong to one explicitly identified
scope, endpoint category, and aligned UTC window.

The producer must not merge unrelated identities into one
account-scoped event stream.

Multiple verified outcomes for the same request may be merged
by the aggregator only within its existing identity, category,
timestamp, and request-ID consistency rules.

## 13. Delivery and loss accounting

A future collector must separately specify its enqueue, delivery,
retry, deduplication, and failure semantics.

Dropped events, queue overflow, producer errors, process restarts,
unobserved workers, and incomplete delivery cannot be ignored.

A bounded in-memory buffer by itself does not establish durable
capture or completeness across processes.

No atomic shared collector is implemented by this contract.

## 14. Completeness attestation

The aggregate_request_events complete=True argument is a claim
supplied by its caller, not proof of complete instrumentation.

The producer or collection coordinator must require independently
supported evidence for coverage of the relevant identity scope,
endpoint category, and UTC window.

A zero-event interval is complete only when coverage can
independently establish that zero relevant events were observed
without capture gaps.

If completeness cannot be established, downstream counters must
remain unknown, and conversion to a valid AbuseObservation
must not proceed.

Completeness cannot be inferred from successful function execution,
absence of exceptions, or nonempty counters.

## 15. Privacy and data minimization

Raw credentials, access tokens, session secrets, request bodies,
and unnecessary personal information must never be stored in
SecurityRequestEvent records.

Identity scope identifiers, network-derived identifiers, retention,
access permissions, audit logging, and erasure obligations require
an approved privacy design before live telemetry is enabled.

This contract does not authorize any particular retention period.

## 16. Failure policy

Invalid, unverified, missing, or contradictory security evidence
must fail closed for classification eligibility, meaning it must
not be promoted into a valid observation.

Failing closed for observation eligibility does not mean blocking
the user's HTTP request.

No automatic request blocking or account suspension is authorized.

## 17. Proposed isolated producer interface

A future pure producer adapter may accept only explicit,
already-verified server-side facts.

Its result should distinguish:

- an emitted valid SecurityRequestEvent;
- an intentionally unclassified or ineligible event;
- an unavailable or unverified input;
- a telemetry failure requiring a completeness downgrade.

The adapter must not assert provenance merely because its input
parameter is named trusted or verified.

Provenance remains a responsibility of the upstream integrated
authentication, authorization, and request-lifecycle boundary.

No concrete API is approved until the existing application hooks
have been reviewed.

## 18. Validation and test requirements

A future isolated implementation must test at least:

- canonical server-generated request-ID handling;
- rejection of client-controlled identity claims;
- rejection of invalid scope and category values;
- verified authentication and authorization outcomes;
- preservation of overlapping failure signals;
- rejection of malformed and contradictory facts;
- absence of invented negative outcomes;
- UTC timestamp and scope consistency;
- missing evidence and incomplete capture handling;
- bounded identifiers and memory usage;
- deterministic, database-free behavior;
- compatibility with the existing aggregation pipeline.

Tests must not require access to production databases.

## 19. Explicit non-goals

This design does not:

- attach middleware to Django;
- intercept live requests;
- connect Django authentication signals;
- query or write PostgreSQL or SQLite;
- create Redis or another shared collector;
- configure security thresholds;
- approve operational telemetry completeness;
- enable alert delivery;
- activate rate limiting or blocking;
- change production configuration;
- deploy infrastructure.

## 20. Next review gate

Before implementation, review the actual application's
authenticated principal, authorization-decision, endpoint-routing,
request-lifecycle, and deployment topology boundaries.

Only then define a narrowly scoped, non-enforcing producer adapter
and permanent regression tests.

Any future integration must receive its own review and test gate.
