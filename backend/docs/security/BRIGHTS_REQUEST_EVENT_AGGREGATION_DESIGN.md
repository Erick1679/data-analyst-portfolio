# Brights Security Shield — Request-Event Aggregation Design

## 1. Status and scope

Status: Proposed engineering design.

This document defines an isolated request-event aggregation
component for future security telemetry.

It does not approve a production collector, shared counter
backend, middleware integration, rate limiter, or blocker.

Actual Django authentication and authorization event producers
must be inspected before live instrumentation.

## 2. Relationship to committed components

The aggregator will use the committed fixed UTC window utility
to assign integer Unix timestamps to half-open windows.

The aggregator will produce validated counters compatible
with the committed abuse-observation evaluator.

The signal-collection contract remains authoritative for
counter overlap, telemetry completeness, and scope isolation.

No direct integration with live Django requests is authorized.

## 3. Event model

A proposed immutable event contains:

- request_id
- timestamp_seconds
- identity_scope_type
- identity_scope_id
- endpoint_category
- authentication_failed
- authorization_denied

An event represents evidence relating to one eligible request.

Request identifiers must be stable and generated by a
trusted source. Untrusted arbitrary client-supplied values
must not be accepted as authoritative request identities.

Identity scope types must come from an explicitly approved
enumeration rather than arbitrary strings.

Endpoint categories must match reviewed classification rules.

Boolean security outcomes require authoritative event sources.

## 4. Identity scope isolation

Events may be aggregated only when their identity scope
type and identity scope identifier match.

The aggregator must not combine unrelated accounts,
organizations, credentials, or immediate network peers.

A network peer is not equivalent to an authenticated user.

The committed client-IP helper identifies the immediate
network peer, not necessarily the originating internet client.

The choice of identity scope requires separate approval.

## 5. UTC window assignment

All accepted events must carry integer Unix timestamps
measured in seconds.

Use fixed_utc_window(timestamp_seconds, duration_seconds).

The interval includes the start timestamp and excludes
the end timestamp.

Events exactly at the end boundary belong to the next window.

The same duration must apply to every event contributing
to one observation.

The aggregation duration is supplied explicitly and must
not be silently selected from a production default.

## 6. Request deduplication

Within one scope and window, a distinct request_id
contributes at most once to request_count.

Repeated delivery of the same event must not increase
the count.

Different signal evidence for the same request may update
the authentication or authorization counters independently.

A request may contribute to both failure counters.

Duplicate event records must be idempotent.

A request identifier reused across different legitimate
windows is treated according to its window assignment.

## 7. Conflicting event evidence

The design must distinguish duplicates from conflicting
records sharing a request identity.

For example, the same request may first appear with one
verified failure signal and later with a second verified
failure signal.

An approved aggregation policy must define whether to
merge corroborated signal evidence or reject conflicts.

The initial pure implementation should use an explicitly
documented deterministic policy.

It must never depend on arbitrary event input order.

Malformed or contradictory evidence must not be silently
converted into clean telemetry.

## 8. Independent security counters

request_count is the number of distinct eligible requests
within the selected scope and observation window.

authentication_failures counts distinct requests with
verified authentication failure evidence.

authorization_denials counts distinct requests with
verified authorization denial evidence.

Both failure counters must independently remain less than
or equal to request_count.

Their sum may exceed request_count.

HTTP response status alone is insufficient to establish
an authoritative authentication or authorization outcome.

## 9. Telemetry completeness

Incomplete telemetry must not be interpreted as zero failures.

A future aggregate result must explicitly distinguish
complete and incomplete event evidence.

A zero-event window is valid only when the collection
system can establish that the window is complete.

The pure aggregator cannot independently prove that
all real requests were collected.

Completeness must therefore be supplied or established
by a separately verified collection layer.

Unknown or invalid evidence must not silently result
in a NORMAL abuse classification.

## 10. Invalid input handling

Reject or return an explicitly invalid result for:

- Non-integer timestamps, including booleans.
- Invalid or non-positive window durations.
- Missing or untrusted request identifiers.
- Invalid identity scope identifiers.
- Unsupported identity scope types.
- Unsupported endpoint categories.
- Non-boolean security outcome fields.
- Contradictory identities for the same request.
- Unapproved combinations of scopes or windows.

No invalid input may activate enforcement.

The initial pure implementation must define whether
a malformed batch fails as a whole rather than silently
dropping invalid events.

## 11. Deterministic aggregation

Identical accepted inputs must produce identical results.

Input order must not affect counters or classification.

Deduplication must not depend on unstable hash ordering.

The aggregation result should be immutable.

No system clock access is required for pure evaluation.

No database, network, logging, cache, or middleware
dependency belongs in the pure aggregation utility.

## 12. Result contract

A future aggregation result should contain:

- identity_scope_type
- identity_scope_id
- endpoint_category
- window_start_seconds
- window_end_seconds
- window_seconds
- request_count
- authentication_failures
- authorization_denials
- complete
- valid

The result must support a separate conversion step
to the existing AbuseObservation structure.

Conversion is permitted only after required inputs,
identity scope, window, and completeness are validated.

This design does not change the existing evaluator API.

## 13. Privacy and resource limits

Do not store passwords, tokens, raw request bodies,
or private authorization headers as aggregation keys.

Use the minimum event metadata needed for analysis.

A future production implementation requires bounded
memory, event retention, input sizes, and state expiration.

A pure implementation should also reject unsupported
data shapes and avoid unnecessary data retention.

No storage technology or retention period is approved here.

## 14. Multi-instance considerations

Pure in-memory aggregation is suitable only for isolated
tests and deterministic calculations.

It does not solve production event delivery, concurrency,
cross-instance deduplication, or shared state consistency.

A production system requires separate design approval
for atomic aggregation, event transport, lifecycle,
retention, reliability, and failure recovery.

No production throughput guarantee is established.

## 15. Required isolated regression tests

Test the following behavior before integration:

- One valid request in one UTC window.
- Several distinct requests in one scope.
- Exact start and end window boundaries.
- Same request delivered multiple times.
- Same request with both verified failure signals.
- Reordered event inputs producing equal results.
- Different accounts remaining isolated.
- Different endpoint categories remaining isolated.
- Individually bounded overlapping failure counts.
- Invalid timestamps and durations.
- Invalid request and scope identifiers.
- Non-boolean security outcome values.
- Conflicting evidence for one request identity.
- Missing or incomplete telemetry.
- Complete zero-event windows.
- Immutable aggregation results.
- No database or network access.
- No live middleware or enforcement integration.

## 16. Implementation sequence

1. Commit and review this design.
2. Define immutable event and aggregation result structures.
3. Implement a pure deterministic aggregation function.
4. Add database-free unit regression tests.
5. Verify all existing security regression tests.
6. Commit only approved isolated files.
7. Inspect actual Django authentication and permission paths.
8. Review telemetry completeness and concurrency.
9. Design an approved collector separately.
10. Require explicit approval before any production enforcement.

## 17. Security release boundaries

Event collection, aggregation, observation classification,
policy decisions, and enforcement are separate components.

No event aggregation result authorizes blocking or throttling.

Existing authentication, permissions, and tenant isolation
must remain unchanged.

No Django settings, middleware, database migrations,
GitHub push, or infrastructure deployment are authorized
by this design.
